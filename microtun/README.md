# microtun v2 — VPN سبک UDP برای بازی

هستهٔ تونل TUN روی UDP، با کمترین سربار و تأخیر. ویژگی اصلی نسخهٔ اول حفظ شده: پکت‌های کوچک (بازی) دوبار فرستاده می‌شن تا یک پکت گم‌شده باعث لگ نشه.

| | WireGuard | microtun v1 (نسخهٔ اولیه) | **microtun v2** |
|---|---|---|---|
| سربار هر پکت | 32 بایت | 37 بایت | **28 بایت** |
| رمزنگاری | ChaCha20-Poly1305 | AES-256-GCM | AES-256-GCM |
| هندشیک / Forward secrecy | دارد | ندارد (کلید ثابت) | **X25519 + PSK، دارد** |
| تعویض خودکار کلید | هر 2 دقیقه | ندارد | **هر 2 دقیقه، بدون قطعی** |
| چند کاربر | دارد | فقط 1 | **دارد (کلید جدا برای هر کاربر)** |
| هدر روی سیم | ثابت و قابل شناسایی | 8 بایت ثابت + شمارنده | **ماسک‌شده، بدون بایت ثابت** |
| ارسال دوبارهٔ پکت کوچک | ندارد | دارد | **دارد** |
| ریستارت سرور | خودش وصل می‌شه | کلاینت خاموش می‌شد | **حدود 5 ثانیه بعد وصل می‌شه** |
| keepalive برای NAT | دارد | ندارد | **دارد** |

داده‌ها مثل نسخهٔ اول فقط **یک بار AES-GCM** دارن. هندشیک (X25519) فقط موقع اتصال و هر ۲ دقیقه یک بار انجام می‌شه، پس هیچ هزینه‌ای به هر پکت بازی اضافه نمی‌کنه.

## نتیجهٔ تست (آزمایشگاه شبکهٔ مجازی، سرور و کلاینت جدا)

- اتصال و هندشیک: ۱ تا ۳ میلی‌ثانیه. ping داخل تونل و خروج از NAT سرور اوکی بود.
- با **۲۰٪ پکت‌لاس در هر جهت** (۱۰۰۰ پینگ):
  - burst روشن: **8.4٪** لاس
  - burst خاموش: 34.8٪ لاس
- دانلود ۳۰ مگابایت از طریق تونل: هش sha256 سالم بود و پکت‌های بزرگ دوبار فرستاده نشدن.
- ریستارت سرور وسط کار: کلاینت **حدود ۵ ثانیه** بعد خودش دوباره وصل شد.

## نصب سرور (سرور خارج)

```bash
git clone https://github.com/kankiturk8770/Labo.git && cd Labo/microtun
sudo bash install.sh server SERVER_PUBLIC_IP 51820 1
```

`/etc/microtun/server.json` و `/etc/microtun/client1.json` ساخته می‌شن و سرویس `microtun-server` بالا میاد. اگه فایروال فعاله، پورت UDP رو باز کنید.

## نصب کلاینت لینوکس (برای تست)

فایل `client1.json` رو به دستگاه کلاینت ببرید و بعد:

```bash
cd Labo/microtun
sudo bash install.sh client ./client1.json
ping 10.66.66.1             # سرور داخل تونل
curl ifconfig.me            # باید IP سرور رو نشون بده (route_all روشنه)
```

**با لینک پنل کانکی:** در پنل، بخش microtun › «لینک تست»، کاربر رو انتخاب کن و لینک رو کپی کن:

```bash
sudo microtun client -url 'mtun://…'                    # کل ترافیک از تونل
sudo microtun client -url 'mtun://…' -route-all=false   # فقط شبکهٔ تونل
sudo microtun client -url 'mtun://…' -device laptop2    # دستگاه دوم همان کاربر روی همین سیستم
```

از نسخهٔ ۲.۱ هر دستگاه یک شناسهٔ ثابت دارد (از `/etc/machine-id`)، پس ری‌استارت کلاینت همان دستگاه حساب می‌شود و همان آدرس را می‌گیرد. سرور پنل به دستگاه دوم و سوم کاربر آدرس جدا می‌دهد و اگر IPv6 داشته باشد، IPv6 هم می‌دهد.

اجرای دستی بدون systemd: `sudo microtun client -c client1.json`. خاموش کردنش (Ctrl+C) مسیرها رو برمی‌گردونه.

## تنظیمات مهم

| کلید | توضیح |
|---|---|
| `burst_max` | پکت‌های IP تا این اندازه (بایت) دوبار فرستاده می‌شن؛ `0` یعنی خاموش. پیش‌فرض 300 (بازی‌ها معمولاً 50 تا 200 بایت). |
| `burst_delay` | فاصلهٔ نسخهٔ دوم، پیش‌فرض `2ms`. اگه لاس پشت‌سرهم (burst loss) دارید، بیشترش کنید، مثلاً `5ms`. |
| `mtu` | پیش‌فرض 1420. |
| `keepalive` | فقط کلاینت؛ پیش‌فرض `10s` تا NAT اپراتور مسیر رو نبنده. |
| `route_all` | کل ترافیک IPv4 از تونل بره. `false` یعنی فقط شبکهٔ تونل. |
| `nat` | فقط سرور؛ ip_forward و MASQUERADE رو خودش تنظیم می‌کنه. |
| `obfs_key` | روی سرور و همهٔ کلاینت‌هاش یکیه؛ فقط هدر رو مخفی می‌کنه. |
| `key` | کلید اختصاصی هر کاربر (`microtun genkey`). |

**افزودن کاربر:** یک `key` با `microtun genkey` بسازید و یک IP آزاد از شبکهٔ تونل انتخاب کنید. یک خط به `peers` در `server.json` اضافه کنید، و یک کپی از `client1.json` با همون `key` و `address` بسازید. بعد: `systemctl restart microtun-server`.

## در تونل (ایران ← خارج)

microtun یک پورت UDP ساده‌ست، پس مثل بقیهٔ پروتکل‌ها می‌تونه پشت تانل یا فورواردِ پورتِ UDP بره. در کلاینت، `server` رو IP و پورت ایران بذارید.

## محدودیت‌های فعلی

- فعلاً فقط لینوکس (کلاینت اندروید و ویندوز مرحلهٔ بعده).
- سرور Go این ریپو هنوز یک دستگاه برای هر کاربر و فقط IPv4 دارد؛ چند دستگاه و IPv6 کار سرور پنل کانکی است (کلاینت با هر دو کار می‌کند).
- ساعت کلاینت: از ۲.۱ اگر ساعت عقب برود هم وصل می‌شود، به شرطی که با ساعت سرور بیشتر از ۱۲۰ ثانیه فرق نداشته باشد.
- دو نسخهٔ یکسان از یک پکت روی سیم دیده می‌شه. این بهای ضد لاس بودنه.

## پروتکل

```
[ idx 4 | counter 8 ]  ← ماسک با AES(obfs_key, 16 بایت اول ciphertext)
[ AES-256-GCM ciphertext | tag 16 ]   nonce = هدر بدون ماسک
```

- `idx = 0` یعنی پکت هندشیک.
- **Init (کلاینت):** کلید موقت X25519، timestamp، idx کلاینت و پدینگ تصادفی. رمز با کلید مشتق از PSK.
- **Response (سرور):** کلید موقت سرور و idx دو طرف. هیچ‌وقت از init بزرگ‌تر نیست، پس amplification نداره.
- **۲.۱ (داخل پدینگ، پس نسخهٔ ۲.۰ نادیده‌اش می‌گیره):** init می‌تونه `mtD1` + شناسهٔ دستگاه (۸ بایت) داشته باشه و response در جوابش `mtA1` + IPv4 + یک بایت پرچم + IPv6 دستگاه.
- کلیدهای جلسه = HKDF(X25519 shared, salt = PSK, info = هر دو کلید موقت و هر دو idx).
- **ضد replay:** پنجرهٔ ۱۰۲۴ پکتی. init قدیمی‌تر از آخرین init فقط وقتی پذیرفته می‌شه که نزدیک ساعت سرور (۱۲۰ ثانیه) و کلید موقتش تازه باشه. جلسهٔ جدید فقط وقتی جای قبلی رو می‌گیره که اولین پکت دادهٔ معتبر روش برسه.
- سرور آدرس کلاینت رو فقط بعد از یک پکت احراز‌شده و غیرتکراری عوض می‌کنه. پکت‌هایی که IP مبدأشون مال اون کاربر نیست دور ریخته می‌شن.
